# VALIDATION — 검증 기준

## 0. 실행 — 손으로 확인하지 않습니다

```
node tools/check.mjs                    정적 + DOM (1회 로드)
node tools/check.mjs --full             + 18조합(6폭 × 3구성) 레이아웃
node tools/check.mjs --status           docs/STATUS.md 갱신 (실측 단일 출처)
node tools/check.mjs --record           아래 5절 기록 블록 출력
node tools/check.mjs --static           브라우저 없이 정적 검사만
```

**2절의 판정 기준은 `tools/check.mjs` 에 구현되어 있습니다.** 이 문서는 *무엇을 왜 보는가*를,
스크립트는 *어떻게 판정하는가*를 담습니다. 항목을 추가할 때는 **둘을 함께** 고칩니다.

### 왜 자동화했는가
2절 17항목 × 18조합 = 300여 판정을 사람이 눈으로 보고 결과를 손으로 5절에 전사하고 있었습니다.
그런데 항목의 성격이 섞여 있습니다 — **태그 정합 · id 중복 · 행 중첩 · 콜아웃 정합 · 죽은 칩 ·
결번 · 물량 · 배지 규격 · 도면 생성 · 구성 소속**은 **폭과 무관**해 1회 로드로 끝납니다.
이걸 18번 확인하는 것은 낭비였고, 그래서 「이전 PASS 승계 금지」 규칙이 실제로는 지켜지기 어려웠습니다.
스크립트는 매번 전부 다시 측정합니다.

### 실행 환경
- Chromium 은 `/opt/pw-browsers/chromium` (Playwright 별도 설치 불필요).
- 로컬 Windows 작업 폴더에는 네트워크가 없어 패키지 설치가 안 됩니다 — `--static` 은 **`node` 만으로** 돕니다.
  (2026-08-20: 태그 검사를 `python3` + `html.parser` 에서 Node 구현으로 이관했습니다 — Windows 에서 `python3` 이
  스토어 스텁으로 잡혀 실행이 실패했습니다. 검사 결과는 이관 전후 동일함을 대조 확인했습니다.)
- `playwright` 를 찾지 못하면 스크립트가 정적 검사만 수행하고 그 사실을 출력합니다(조용히 통과하지 않습니다).
- 종료 코드 — `0` 전건 PASS / `1` FAIL 있음 / `2` 실행 실패.

### 설계 원칙 — 판정 로직을 다시 쓰지 않는다
정의 수집은 페이지의 `fsTipBuild()`, 도면 생성은 `fsPopPaint()`, 변경 이력 집계는 `fsLogHead()` 와
**같은 셀렉터**를 씁니다. 검사가 구현을 다시 구현하면 둘이 갈라지고, 그때는 검사를 믿을 수 없게 됩니다.

## 4. 테스트 케이스 탭과의 관계
`rt-tc` 탭의 케이스는 **설계 대상 화면(S-02)의 기능 검증**입니다.
이 문서의 매트릭스는 **리포트 문서 자체의 렌더링 검증**입니다. 둘은 별개이며 둘 다 수행합니다.

| | 대상 | 수행 시점 |
|---|---|---|
| 이 문서 · `check.mjs` | `index.html` 렌더링 · 정합 | 문서 수정 직후 (자동) |
| `rt-tc` 탭 케이스 | S-02 화면 동작 | 프로토타입 확인 가능분 먼저 / 나머지는 개발 착수 후 |

> **건수를 여기에 적지 않습니다.** 종전에 이 절 안에서 「116건」과 「06 탭 106건」이 함께 적혀
> 서로 어긋나 있었습니다. 현재 집계는 `docs/STATUS.md` 와 `check.mjs` 의 `D12` 항목이 출력합니다.

06 탭 케이스의 **정의는 `index.html`**, **수행 기록은 외부 시트**가 담당합니다. 명세가 바뀌면 탭을 먼저 고치고 시트 A~I열을 갱신하며, 수행 기록(J~M열)은 덮어쓰지 않습니다.
